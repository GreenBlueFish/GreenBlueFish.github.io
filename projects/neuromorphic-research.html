Spiking Neural Network Accelerator

Custom spiking neural network (SNN) hardware accelerator designed to train and run SNN models.

View on GitHub ↗

Motivation and Approach

Why I built this

During my 2A term I came across spiking neural networks (SNNs) and neuromorphic computing through research papers and articles. Between building neural network libraries from scratch and building my own computers, neuromorphic computing sat right at the intersection of the two things I like designing most. I worked through a stack of papers and textbooks to get a solid grip on the basics of SNNs and neuromorphic hardware before committing to a design. Below is a list of some of the most influential papers and textbooks I read.

  • A New Era in Computing: A Review of Neuromorphic Computing Chip Architecture and Applications
  • A Quarter of a Century of Neuromorphic Architectures on FPGAs - an Overview
  • Review of Recent Developments in Neuromorphic Computing Based on Emerging Memory Devices
  • Neuronal Dynamics - Textbook
  • Neuroscience 5th Edition - Textbook

Once I'd worked through the papers and textbooks, I wanted to put that knowledge into an actual accelerator rather than leave it as reading notes. I put together a team of three, myself along with Melika M. and Ron Kazachkov, and after comparing a few candidate papers we settled on implementing Unsupervised learning of digit recognition using spike-timing-dependent plasticity. The paper trains an SNN on the MNIST dataset in a fully unsupervised setting. We chose to simplify the neuron dynamics to make the hardware implementation more tractable (in hindsight, this cost us accuracy). Below are the four equations that define our model.

  1. Neuron Updating (Forward prop): Xpostdata += (Xpre1firing & Wpost1 + Xpre2firing & Wpost2 + ... + Xprenfiring & Wpostn)
  2. Threshold/Reset: if Xdata > Xthreshold then Xdata = Xreset and Xfiring = 1
  3. Weight Updating (STDP): (A+ * Xpredata) & Xpostfiring - (A- * Xpostdata) & Xprefiring
  4. Forward Step in Time: Xdata *= decay_rate, where 0 < decay_rate < 1

Here, X is a 16-bit neuron value: the lower 15 bits are a Q1.14 fixed-point number (Xdata), and the most significant bit is the firing bit (Xfiring), which is 0 if the neuron didn't just fire and 1 if it did. Xpost denotes a postsynaptic neuron and Xpre a presynaptic neuron. W is a 15-bit Q1.14 weight value representing a synaptic weight. The remaining values (Xthreshold, Xreset, A+, A-, decay_rate) are model presets.

I built a logic block (seen below) in Verilog to implement these equations directly in hardware. I designed it to use only a single DSP slice per logic block, since I wanted to maximize the number of logic blocks I could fit on the board — the target FPGA (a Zynq 7020 SoC) only has 220 DSP slices to work with.

Once I had a working logic block, I used it as the building block for a scalable architecture (shown below). The design was shaped around the fact that the Zynq 7020 SoC exposes 35 BRAM slices once configured. The plan was to store all neuron values in 1-3 of those slices and dedicate the remaining 32-34 slices to storing synaptic weights.

After implementing the architecture in Verilog, I wrote a Python (cocotb) test bench for running and validating models on the network. Unfortunately, after all that work, one of my teammates found that the neuron equations we'd chosen didn't hold up well on MNIST — the best accuracy we could get was 85%. Because of this, I've decided not to scale the design up to the full-size SNN model in my test bench; it would take a lot more code, and it's not worth writing for a model I already know underperforms.

Reflection

What I learned

There are a few key lessons I took away from building this accelerator. The most important one is that, before starting on an accelerator, I need to nail down the right equations first. This was hard to get right here: I wanted to get started as quickly as possible to leave myself the most time to actually build, so I picked equations that seemed roughly reasonable rather than validating them first. None of us on the team took the time to test whether the equations actually worked before committing to them in hardware, which in hindsight was a mistake. My teammates have since moved on to testing other equation sets, so by the time I start a second accelerator I should have a much better sense of what actually works.

Another thing I should have watched more closely is LUT usage. I was so focused on fitting one DSP slice per logic block that I lost track of the FPGA's LUT budget entirely. After doing the math by hand, I found I'd fall well short of the LUTs needed to implement the full accelerator at 220 logic blocks (one per DSP slice). On top of that, what I built isn't really a neuromorphic computer — it's an SNN accelerator. That's a fine result for this project, but going forward I'd like to design something closer to an actual neuromorphic computer that sidesteps the Von Neumann bottleneck my current design still has.

One more thing I'd change: I want to use fewer control signals where possible (I did try to keep this in check here), and where I do need many, adopt a real naming convention instead of naming wires whatever made sense in the moment. Concretely, that means a reference doc where I can look up a signal name and its etymology to figure out what it does — something that would help a lot once the number of control signals grows, and would make it far easier for someone else to review my work. Finally, my next accelerator won't be a solo effort — this one could have gone further, but I had to make design compromises to avoid the extra work that certain choices would have created for a single person.
